# 양식 · 장 구성 · ID 규칙

SKILL.md에서 단계마다 가리키는 양식이다. 장마다 **제목 · 한 줄 목적 · 필요한 표의 열**만 적었다. 예시 내용은 일부러 넣지 않았다 — 다른 프로젝트의 내용을 그대로 베끼게 되기 때문이다.

## 목차

1. 결정 기록 파일 · 2. 프로필 → 장 선택 · 3. PRD 장 구성 · 4. 기능명세서 장 구성 · 5. ID 규칙 · 6. `docs/README.md` · 7. 요청 문서 · 파트 안내 · 루트 `CLAUDE.md` · 8. 다음 문서 안내

## 1. 결정 기록 파일 (`docs/정리/결정-인터뷰.md`)

기준 문서가 아니다. 두 문서를 쓰기 위한 결정을 받는 즉시 적는 기록이고, 두 문서는 이 기록만 보고 쓴다.

```markdown
# 결정 인터뷰 기록 — PRD·기능명세서 작성

> 기준 문서가 아니다. 결정 인터뷰의 답을 받는 즉시 적는 기록이다. 두 문서가 완성된 뒤 내용이 다르면 두 문서가 맞다.

| 항목 | 내용 |
|---|---|
| 시작 | YYYY-MM-DD |
| 입력 자료 | (읽은 자료 목록) |
| 진행 | ① 문서 틀 → ② 프로필 → … (끝난 갈래에 ✅) |

## 1. 입력 자료에서 확인한 사실
- (자료에서 확인한 사실 · 찾지 못한 원자료)
| # | 한쪽 | 다른 쪽 |   ← 자료 안에서 같은 대상에 값이 둘 이상인 곳(X 후보)

## 2. 결정
### Qn 제목 — 결정 YYYY-MM-DD (결정자, 추천안/수정안)
- (결정 내용. 이유가 중요한 결정은 "이유:"를 함께)

## 3. 작성 결과
- 만든 것 · 점검 결과 · 결정에 없던 것(사용자 확인 여부) · 완료 점검 요약

## 4. 남은 질문
- (남은 질문) · 보낸 요청(⏳/✅) · 요청 예정
```

## 2. 프로필 → 장 선택

갈래 2(프로필)의 답으로 장을 고른 뒤 **번호를 다시 매기고, 두 문서의 장 목록을 작성 전에 사용자에게 보여 확정한다.**

| 장 | 넣는 조건 |
|---|---|
| PRD 평가 기준 대응(5장 안 절) | 대회 · 심사가 있을 때 |
| PRD 개인정보(7장 안 절) | 개인정보를 다룰 때 |
| PRD AI의 역할(7장 안 절) | AI · 모델을 쓸 때 |
| PRD 팀 · 협업 | 팀일 때(혼자면 저장소 · 현재 상태만 남긴 짧은 장) |
| PRD 일정 · 마일스톤 | 문서가 일정을 관리할 때 |
| PRD 기획서에서 바뀐 점 + X 표 | 기획서가 있을 때 |
| 명세 상태 전이(3장 안 절) | 상태가 있는 대상이 있을 때 |
| 명세 화면 | 화면이 있을 때 |
| 명세 산출물 | 사용자에게 주는 파일이 있을 때 |
| 명세 데이터 · API | 저장 · 서버가 있을 때 |
| 명세 외부 API 사용 명세 | 외부 API · 데이터가 핵심일 때 |
| 명세 시연(수용 기준 장 안 절) | 시연 · 데모가 있을 때 |
| 명세 지표 수집(이벤트) | 성과를 이벤트로 재야 할 때 |
| 그 밖의 장 | 항상 |

## 3. PRD 장 구성

|---|---|---|
| 머리 | 한 줄 요약 인용 + 문서 정보 | 항목 · 내용(문서 · 짝 문서 · 버전 · 팀 · 권한 "두 문서가 유일한 기준") |
| 0.1 문서 체계 | 어떤 문서가 기준이고 무엇이 아닌가. **값은 한 곳에만** 문장(이 문서가 원본인 것 / 명세가 원본인 것). 참조 규칙(저장소 안 경로만) | 층 · 문서 · 역할 (기준 · 세부 문서 · 점검 · 원본 자료 · 기록 · 협업 · 안내 · 외부 근거) |
| 0.2 표기 | ID와 출처 표기 | 표기 · 뜻 (F · R · S · A · AC · U · RK · E · X, ⚠ U-xx, ⏳) / 출처 표기 · 뜻 (기획서 인용 · 측정값 · 팀 설계값 · 목표 · 가설 · 외부 인용 · 결정) |
| 0.3 용어집 | 두 문서가 같은 뜻으로 쓸 용어. 용어 이름에 든 숫자는 이름이고 값은 설정값 표라는 문장 | 용어 · 뜻 (서비스 용어 / 도메인 · 제도 용어 — 외부 값은 1차 출처 뒤 / 쓰지 않는 말은 문구 규칙으로) |
| 1 한 줄 정의 | 무엇을 하는가 + 이것이 아닌 것 | — |
| 2 배경과 문제 | 문제와 근거 | 문제 · 내용 · 근거(〔E-nn〕) |
| 3 서비스 정의 · 차별점 | 사용자 관점의 단계, 차별점 | 비교 대상 · 그쪽의 방식 · 우리 |
| 4 사용자 · 시나리오 | 사용자 계층 · 권한 · 시나리오(단계마다 화면 ID) · 흐름 요약 | 사용자 · 하는 일 · 쓰는 곳 · 근거 |
| 5 목표 · 지표 | (대회) 평가 기준 대응, 이번 단계에서 잴 것, 제출물 · 발표, 쓰지 않는 수치. **목표치의 원본은 여기다** | 항목 · 배점 · 평가 내용 · 우리의 답 · 보여줄 것 / # · 잴 것 · 목표 · 담당 · 비고 |
| 6 범위 | 이번 단계 · 선택 · 로드맵 · 하지 않는 것 | # · 기능 · 근거 · 기능 ID / # · 기능 · 근거 · 착수 조건 / 항목 · 내용 · 근거 / 하지 않는 것 · 근거 |
| 7 원칙 | 개인정보 · 불확실성 · 한계 표시 · 문구 규칙 · 숫자 표시 · AI의 역할 | 항목 · 원칙 / 불확실성 · 표시 방법 / 쓰지 않는 표현 · 쓰는 표현 · 근거 / 구분 · 무엇 · 이유 |
| 8 제약 · 위험 · 미확정 | 제약, 위험, 미확정 | ID · 위험 · 대응 · 관련 / **ID · 미확정 · 지금 아는 것 · 누가 정함 · 정해지면 바뀌는 곳** |
| 9 팀 · 협업 | 팀 · 결정권 · 협업 장치 · 저장소 · 현재 상태 | 파트 · 맡는 것 · 폴더 / 구성 · 상태 |
| (일정) | 마일스톤 | 날짜 · 일 |
| 10 기획서에서 바뀐 점 | 기획서와 다르게 정한 것, 기획서 안에서 값이 둘 이상인 곳 | # · 기획서 · 이번 · 이유 · 결정 / ID · 한쪽 · 다른 쪽 · 정하는 곳 |
| 11 결정 이력 | 날짜별 결정 요약(세부는 결정 기록) | 날짜 · 결정 |

- 미확정 표의 U가 해소되면 행을 지우지 않고 "지금 아는 것" 칸을 `**확정 YYYY-MM-DD**: …`로 시작하게 바꾼다(점검 스크립트가 해소된 U로 본다).
- "본선" 같은 단계 이름은 프로젝트의 이번 단계 이름(첫 출시 · MVP · 1차 개발 등)으로 바꾼다.

## 5. ID 규칙 (점검 스크립트가 이 규칙으로 읽는다)

| ID | 형식 | 정의하는 곳 |
|---|---|---|
| 기능 | `F-영대문자-두자리` (F-AUTH-01) | 명세 2장 표 첫 칸 |
| 규칙 | `R-영대문자-두자리` (R-AUTH-01) | 명세 3장 표 첫 칸 — `R-AUTH-01 이름`처럼 이름을 붙여도 정의로 본다 |
| 수용 기준 | `AC-영대문자-두자리` (AC-AUTH-01, AC-DEMO-01) | 명세 9장 표 첫 칸. 행 안에 검증하는 F를 적는다 |
| 화면 · API | `S-두자리` · `A-두자리` | 명세 4장 · 7장 표 첫 칸 |
| 미확정 · 위험 · 외부 근거 | `U-두자리` · `RK-두자리` · `E-두자리` | PRD 8장 · 부록 A 표 첫 칸 |
| 기획서 불일치 | `X-한자리` | PRD 10장 표 첫 칸 |

- **정의 = 표의 첫 칸에 ID 하나만** 있는 행. 같은 ID를 두 번 정의하지 않는다. 다른 표의 첫 칸에 ID를 넣고 싶으면 "이름 (ID)"처럼 이름을 앞에 둔다.
- 여러 ID는 하나씩 적거나 범위로 적는다: `R-AUTH-01 ~ R-AUTH-04`. `R-AUTH-01·02` 같은 줄임은 점검 스크립트가 읽지 못한다.
- 절 참조는 "PRD 7.3" · "기능명세서 1.4"(문서 이름 = 파일 이름), 같은 문서 안은 "(3.5)" · "5장".
- 기능명세서의 모든 F는 PRD 어딘가(보통 범위 장)에서 한 번 이상 가리켜야 한다.

## 6. `docs/README.md`

```markdown
# {프로젝트} — 문서

> **수정 기록 (YYYY-MM-DD, 파트)** — 무엇을 어떻게 · 왜 · 함께 고친 문서 · 요청   ← (팀이면) 공용 변경 알림판, 최근 5개

(팀이면) 위는 공용 변경 알림판입니다. 기준 문서 · CLAUDE.md가 바뀌면 한 줄씩 남깁니다. 작업을 시작할 때 이 알림판을 봅니다.

## 이 문서를 처음 보신다면
1. PRD.md → 2. 기능명세서.md (두 문서가 유일한 기준, 다르면 함께 고친다) → 3. 고친 뒤 `node docs/check-docs.mjs` → 4. (팀이면) 요청 `request/{내 파트}/`, 회신 `response/{내 파트}/`

## 문서 지도
| 경로 | 내용 | 주 대상 |
(기준 문서 · 점검 스크립트 · 원본 자료 · 정리/ · 원본/ · request/ · response/ · 파트 안내 · **세부 문서 층: 하위 문서가 생기면 여기에 — 기준 문서와 다르면 기준 문서가 이긴다**)

## 형식
### 수정 기록 — `> **수정 기록 (YYYY-MM-DD, 파트)** — …`, 제목 바로 아래, 최신이 위, 최근 5개
### 요청 · 회신 — §7
```

## 7. 요청 문서 · 파트 안내 · 루트 `CLAUDE.md`

**요청 문서** `docs/request/{받는 파트}/YYYY-MM-DD-짧은-제목.md` — 회신은 `docs/response/{요청한 파트}/`(같은 파일명). 스펙 본문은 복사하지 않고 절 번호 · ID를 가리킨다(자료 요청처럼 가리킬 절이 없으면 요청 내용만).

```markdown
# 제목

> **상태: ⏳ 회신 대기** (요청 YYYY-MM-DD, 요청 파트)
> 회신은 `../../response/{요청한 파트}/{같은 파일명}.md`에 들어옵니다.
> **막고 있는 작업**: …

## 왜 요청하나
## 요청 항목
| # | 묶음 | 근거(문서 위치) | 요청할 것 | 올릴 곳 |
## 회신 방법
- 묶음별 올림(위치) / 일부 / 없음, 다르면 다르다고, 반영하지 않기로 해도 회신, 회신을 쓴 사람이 배너를 ✅로
```

회신 뒤 배너: `> **상태: ✅ 회신 완료 (YYYY-MM-DD) — (전부/일부 해결)**` + 회신 위치 · 결론 요약 · 남은 것. 회신 전에 전제가 틀린 것을 알면 본문을 고치고 배너에 `· YYYY-MM-DD 개정`과 이유.

**파트 안내** — 에이전트 개발이면 `{파트}/CLAUDE.md`(규칙) + `{파트}/README.md`(실행 · 구조), 사람 개발이면 `README.md` 하나.

```markdown
# {파트} — 규칙
> **수정 기록 (…)** — …
공통 규칙은 루트 `../CLAUDE.md`.
## (회신 대기 등 먼저 할 것이 있으면) 먼저 할 것
## 담당 — 기능명세서 1.3, 2장 "담당 {파트}"
## 읽을 장 — | 문서 | 장 |
## 정할 것 — 그 파트가 정할 U 목록
## 지킬 것 — 경계 · 원칙 중 그 파트에 걸리는 것(ID로)
```

**루트 `CLAUDE.md` 공통 규칙** — 덧붙이기 전에 사용자에게 묻는다. 기존 내용은 그대로 두고 아래에 덧붙인다.

```markdown
## 공통 작업 규칙
### 작업 시작 시 — 알림판 · 요청/회신 확인 · 파트 규칙
### 기준 — 두 문서뿐 · 값을 지어내지 않는다(U로) · 값은 한 곳에만 · 문구 · 숫자 · 개인정보 원칙 위치
### 문서 갱신 — 구현이 달라지면 같은 작업에서 기준 문서를 고친다 · 수정 기록 · 알림판 · check-docs · 구현 현황
### 협업 — 파트 이름 · 요청 폴더 · 결정권
```

## 8. 다음 문서 안내 (A-6 보고)

이 스킬은 아래 하위 문서를 쓰지 않는다. 프로필에 해당하는 것만 골라 "누가 · 언제 · 어디에"를 안내한다. 파트별 작업 계획은 `superpowers:writing-plans`로 세우고, **그 파트의 U 결정과 하위 문서 작성을 계획의 첫 태스크로** 넣도록 안내한다. 하위 문서는 기준 문서보다 우선하지 않는다 — 다르면 모드 B로 기준 문서를 먼저 고친다.

| 하위 문서 | 필요할 때(프로필) | 누가 | 기준 문서와의 관계 |
|---|---|---|---|
| API 계약서(경로 · 필드 · 타입 · 오류) | 앱과 서버를 다른 사람이 동시에 만들 때 | 서버 파트가 쓰고 앱 파트가 확인 | 명세 API 장의 세부 문서 |
| 작업 계획(태스크 · 착수 조건 · 완료 기준) | 항상, 에이전트 개발이면 특히 | 각 파트(writing-plans) | 기준 문서를 구현 단위로 나눈 것 |
| 화면 설계(와이어프레임 · 디자인 · 화면 세부) | 화면이 있을 때 | 화면 파트 | 명세 화면 장의 세부 문서 |
| 데이터 설계(스키마 · 관계) | 저장소가 있을 때 | 서버 파트 | 명세 데이터 장의 세부 문서 |
| AI 평가 계획(평가셋 · 라벨 기준 · 지표 계산) | AI · 모델을 쓸 때 | AI 파트 | PRD 목표 · 지표를 재는 방법 |
| 진행 기록(끝낸 것 · 판단) | 여러 세션 · 여러 사람이 이어 갈 때 | 각 파트 | 기준 문서가 아니다 |
| 배포 · 운영 안내(실행 · 환경 변수 · 절차) | 서버가 있을 때 | 서버 파트 | 파트 README |
