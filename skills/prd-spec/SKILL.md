# prd-spec — PRD · 기능명세서 작성과 갱신

개발의 기준이 될 문서 두 개를 만든다.

- **PRD** — 왜 · 누구를 위해 · 무엇을 · 어디까지(문제 · 사용자 · 목표 · 범위 · 원칙 · 위험 · 미확정 · 결정 이력)
- **기능명세서** — 어떻게 동작하는가(시스템 구성 · 설정값 · 기능 · 규칙 · 화면 · 데이터 · API · 비기능 · 수용 기준 · 구현 현황)

받침 문서로 **결정 기록**(`docs/정리/결정-인터뷰.md`), **문서 지도**(`docs/README.md`), **점검 스크립트**(`docs/check-docs.mjs`)를 함께 둔다. API 계약서 · 작업 계획 · 화면 설계 같은 하위 문서는 이 스킬이 쓰지 않는다 — 각 파트가 기술 결정을 내린 뒤 쓰는 것이라, 지금 쓰면 지어낸 값으로 채우게 된다(마지막에 "다음 문서 안내"만 한다).

## 원칙 — 왜 이렇게 하는가

1. **기준 문서는 둘뿐이다.** 다른 문서 · 코드와 다르면 두 문서가 맞고, 두 문서끼리 다르면 오류다. 개발자(사람이든 에이전트든)가 무엇을 믿을지 헷갈리지 않게 하려는 것이다.
2. **값을 지어내지 않는다.** 자료 · 코드에서 찾을 수 있는 사실은 찾고, 사용자가 정할 결정은 묻고, 아무도 지금 모르면 **미확정(U)**으로 둔다. 문서가 빈칸을 그럴듯한 값으로 채우면 구현에서 확정값처럼 굳어 버린다. 그래서 "설계 기본값"으로 채우는 장치를 두지 않는다.
3. **값은 한 곳에만 둔다.** 설정값은 기능명세서의 설정값 표, 목표 · 원칙은 PRD. 다른 곳은 숫자를 다시 쓰지 않고 ID · 절 번호로 가리킨다. 같은 숫자가 두 곳에 있으면 한쪽만 고쳐져 어긋난다.
4. **출처를 성격별로 적는다.** 기획서 인용 · 측정값(원자료 위치를 함께, 없으면 "원자료 없음") · 팀 설계값 · 목표 · 가설 · 외부 인용 · 결정(날짜). 기획서의 "이미 한 것"과 "할 계획"을 구분하고, 계획을 완료로 쓰지 않는다.
5. **해마다 바뀌는 외부 사실(제도 · 법 · 요금 · 외부 API 사양)은 1차 출처(원문 주소 · 확인일)가 있어야 확정이다.** 틀리면 사용자에게 잘못된 안내가 나간다. 없으면 U.
6. **결정은 받는 즉시 결정 기록에 적는다.** 인터뷰가 길어지면 대화 앞부분이 요약되며 세부가 사라진다. 두 문서는 결정 기록만 보고 쓴다.
7. **일치는 스크립트로, 스크립트가 못 보는 것은 체크리스트로 확인한다.** "완료"는 체크리스트에 ❌가 없을 때만 말한다.

이 스킬이 보장하는 것은 "지어낸 값이 없음 · 두 문서의 일치 · 빠진 갈래가 없음"까지다. 결정이 옳은지는 인터뷰 답에 달려 있으므로, 결정에 없던 것을 문서에 넣었다면 반드시 따로 보고해 확인받는다.

## 모드 고르기

| 상황 | 모드 |
|---|---|
| 기준 문서가 없다 · 사용자가 처음부터 다시 쓰자고 한다 | **A 새로 작성** |
| 이 스킬의 형식(ID 체계 · 미확정 표)으로 된 기준 문서가 있고, 회신이 왔거나 결정이 바뀌었거나 구현과 문서가 달라졌다 | **B 갱신** |
| 문서는 있지만 이 형식이 아니다(다른 사람이 쓴 PRD 등) | **A** — 기존 문서를 입력 자료로 읽는다 |

## 모드 A — 새로 작성

### A-1 자료 읽기

- 입력 자료를 **모두** 읽는다: 기획서 본문과 그림 · 평가 기준 · 회의록 · 참고 문서 · 기존 코드(기존 서비스에 기능을 더하는 경우). 그림에 흐름도 · 화면 · 실험 결과가 있는 경우가 많으니 그림도 본다.
- PDF는 Read 도구로 먼저 읽고, 실패하거나 한글이 비어 나오면 `scripts/read-pdf.mjs`를 쓴다(아래 "스크립트").
- 결정 기록 파일을 만들고(양식 `references/templates.md` §1) 1장에 적는다: 읽은 자료 목록 · 자료에서 확인한 사실 · 찾지 못한 원자료 · 기획서 안에서 같은 대상에 값이 둘 이상인 곳(X 후보).
- 기획서가 "이미 했다"고 적은 작업(시제품 · 실험 · 분석 · 규칙표 · 참고문헌)의 원본이 있는지 확인한다. 사용자에게 없으면 **그 작업을 한 사람이 있는지 묻는다.** 있으면 원자료 제공 요청을 먼저 보내고(자료 요청은 가리킬 절이 필요 없어 바로 보낼 수 있다), 원본에 달린 질문은 회신 뒤로 미룬다.

### A-2 결정 인터뷰

`references/questions.md`를 읽고 갈래 순서대로 묻는다. 첫 갈래는 문서 틀 확인과 **프로젝트 프로필** — 프로필이 이후 어떤 갈래를 묻고 어떤 장을 쓸지 정한다.

정보가 없을 때:

| 경우 | 할 일 |
|---|---|
| 자료 · 코드 · 공식 문서에서 찾을 수 있는 **사실** | 묻지 않고 찾는다 |
| 사용자가 정할 **결정** | 선택지와 추천을 붙여 묻는다(아래 형식) |
| 사용자도 지금 모르거나 다른 사람이 정한다 | 채우지 않고 **U** — 누가 정하는지와 정해지면 바뀌는 곳을 적는다. 답이 오면 모드 B |
| 프로필상 해당 없음 | 묻지 않고 넘어가고 결정 기록에 "해당 없음" |

질문 형식:

1. **맥락** — 자료에 무엇이 있고 무엇이 없는지, 근거 위치(기획서 쪽수 등)와 함께.
2. **선택지** 2~4개와 각각의 장단점.
3. **추천과 이유** — questions.md의 "추천 기준"에서 끌어낸다. 프로젝트가 달라도 같은 원리로 추천하기 위해서다.
4. **"지금 정하지 않음" 선택지를 늘 둔다**(→ U). 모르는데 고르도록 몰지 않는다.
5. **한 번에 결정 하나.** 서로 붙어 있는 작은 항목만 묶는다.
6. 답은 받는 즉시 결정 기록 2장에 날짜 · 결정자와 함께 적는다.

선택지가 짧고 서로 겹치지 않으면 AskUserQuestion으로 고르게 하고, 표 · 설명이 필요한 결정은 본문에 쓴다. 사용자가 추천 대신 다른 답을 하거나 질문을 되물으면, 그 의도를 반영해 추천을 고쳐 다시 묻는다.

인터뷰 끝에 "두 문서를 지금 쓰고 회신 대기 부분은 U로 둘지 / 회신 뒤 한 번에 쓸지"를 묻는다.

### A-3 장 목록 확정

`references/templates.md` §2의 표로 프로필에서 장을 고르고 번호를 매긴다. **두 문서의 장 목록과 번호를 작성 전에 사용자에게 보이고 확정한다** — 두 문서가 서로 가리키는 절 번호가 쓰는 도중에 바뀌면 참조가 깨진다.

### A-4 작성

순서: ① `docs/README.md` ② `docs/PRD.md` ③ `docs/기능명세서.md` ④ 점검 스크립트 복사(`scripts/check-docs.mjs` → 프로젝트 `docs/check-docs.mjs` — 팀원이 스킬 없이 저장소만으로 점검할 수 있게) ⑤ (프로필이 팀 · 에이전트 개발이면) 파트 안내 문서 ⑥ 루트 `CLAUDE.md` 공통 규칙은 **덧붙이기 전에 묻는다** — 기존 내용은 그대로 두고 아래에 덧붙이며, 고칠 점이 보이면 고치지 않고 보고만 한다.

쓰는 동안:

- 양식과 ID 규칙은 `references/templates.md`. 다른 프로젝트의 내용을 예시로 끌어오지 않는다.
- 결정 사이의 빈틈(삭제 기능이 있는가, 동의는 어느 단위인가 같은 것)을 찾으면 지어 채우지 말고 U로 올리고 **"결정에 없던 것" 목록**에 적는다. 결정에서 논리적으로 따라 나오는 요구(예: 오프라인 동작이면 모델이 앱에 들어 있어야 한다)도 이 목록에 적는다.
- 데이터 · API는 무엇을 저장하고 무엇을 주고받는지까지만 쓴다. 경로 · 필드 · 타입은 파트가 정한다(U).
- 기존 코드에 기능을 더하는 프로젝트면 "현재 동작"과 "바뀔 동작"을 나눠 쓰고, 구현 현황은 실제 상태에서 시작한다.

### A-5 점검

```
node docs/check-docs.mjs                       # 두 기준 문서
node docs/check-docs.mjs --also app/CLAUDE.md  # 파트 문서의 참조까지
node docs/check-docs.mjs --self-test           # 점검기 자체 시험
```

- 오류가 0이 될 때까지 고친다. **첫 실행이 오류 0이면 의심한다** — 자체 시험을 돌리고, 필요하면 복사본에 오류를 일부러 넣어 정말 잡히는지 본다.
- "설정값 반복 후보" 경고는 하나씩 판단한다. 기획서 인용 · 용어 이름에 든 숫자 · 그 문서가 원본인 목표는 허용하고, 나머지는 ID · 절 번호로 바꾼다.

### A-6 완료 점검과 보고

`references/checklist.md`의 모드 A 항목을 확인하고 대화에 표로 보고한다(✅ · ❌ · 해당 없음 + 근거). ❌가 있으면 완료라고 하지 않고 고친 뒤 다시 확인한다. 보고에 넣을 것:

1. 만든 파일과 점검 결과
2. **결정에 없던 것** — 사용자 확인을 받는다
3. 남은 일 — U · 회신 대기 요청
4. **다음 문서 안내** — 프로필에 필요한 하위 문서 · 누가 · 어디에(`references/templates.md` §8). 파트별 작업 계획은 `superpowers:writing-plans`로 세우고, 그 파트의 U 결정과 하위 문서 작성을 계획의 첫 태스크로 넣도록 안내한다. 이 스킬이 writing-plans를 직접 부르지는 않는다.

결정 기록에 "작성 결과" 절을 남긴다. git 커밋 · 저장소 생성은 사용자가 요청할 때만 한다.

## 모드 B — 갱신

1. **무엇이 바뀌었나** — 회신 문서 · 사용자 결정 · 구현과의 차이를 결정 기록에 적는다. 회신으로 미뤄 둔 질문이 열리면 A-2의 질문 형식으로 묻는다.
2. **영향 범위** — 해당 U의 "정해지면 바뀌는 곳"과, 그 U · 관련 ID를 두 문서와 파트 문서에서 검색한 결과.
3. **수정** — 두 문서를 함께 고친다. 해소된 U는 행을 지우지 않고 "지금 아는 것" 칸을 `**확정 YYYY-MM-DD**: …`로 시작하게 바꾸고 본문의 ⚠ 표기를 지운다. 기획서와 달라졌으면 "기획서에서 바뀐 점"에, 결정은 결정 이력에 더한다. 두 문서의 버전 · 수정 기록, 팀이면 변경 알림판도 고친다.
4. **점검** — A-5와 같다.
5. **요청 정리** — 처리한 요청 문서의 상태 배너를 ✅로 바꾸고, 반영하지 않은 것도 회신에 적는다.
6. **완료 점검과 보고** — `references/checklist.md` 모드 B. 결정에 없던 것과 남은 일을 보고한다.

작은 수정 요청(문장 하나, 값 하나)에 인터뷰 전체를 돌리지 않는다. 그 값이 결정을 바꾸는 것이면 결정 기록에 한 줄 남기고 고친다.

## 스크립트

```
node <스킬>/scripts/read-pdf.mjs <PDF 경로> <출력 폴더>
```
쪽마다 텍스트를 `<출력 폴더>/text.txt`에, 내장 그림을 `p{쪽}_img{n}.png`로 꺼낸다. 처음 실행할 때 `pdfjs-dist`를 임시 폴더에 설치한다(Node만 있으면 된다). 출력 폴더는 작업용 임시 폴더로 하고, 꺼낸 그림은 Read 도구로 본다. 한글 CMap이 없어 `pdftotext`가 한글을 못 뽑거나, 페이지 렌더링이 큰 그림에서 죽을 때 쓰려고 만든 스크립트다.

```
node docs/check-docs.mjs [PRD 경로] [명세 경로] [--also 파일 ...] [--self-test]
```
기본 경로는 스크립트와 같은 폴더의 `PRD.md` · `기능명세서.md`. 문서끼리 가리킬 때 쓰는 이름("PRD 7.3", "기능명세서 1.4")은 파일 이름에서 가져온다 — 영어 프로젝트에서 `SPEC.md`를 쓰면 "SPEC 1.4"로 가리킨다.

## 언어와 문체

만드는 문서는 프로젝트 언어를 따르고 기본은 한국어다. 짧은 평서문("~다"), 장마다 표, 숫자는 출처와 함께. 사용자에게 하는 보고와 질문은 사용자의 언어로 한다.
