# prd-spec

기획서 · 아이디어 메모 · 회의록 · 기존 코드에서 출발해 **결정 인터뷰**를 거쳐 **PRD**와 **기능명세서**를 쓰고, 두 문서가 어긋나지 않는지 점검까지 하는 Claude Code 스킬입니다. 문서가 생긴 뒤 회신이 오거나 결정이 바뀌면 같은 스킬로 갱신합니다.

- **값을 지어내지 않습니다.** 자료에서 찾을 수 있는 사실은 찾고, 결정은 선택지와 추천을 붙여 묻고, 아무도 지금 모르는 값은 **미확정(U)** 으로 남깁니다.
- **두 문서가 유일한 기준입니다.** PRD는 왜 · 누구 · 무엇 · 어디까지, 기능명세서는 어떻게 동작하는가를 맡고, 같은 값은 한 곳에만 둡니다.
- **일치는 스크립트로 확인합니다.** ID 정의 · 참조 · 절 번호 · 기능↔수용 기준 · 범위 일치를 점검하고, 스크립트가 못 보는 것은 완료 체크리스트로 확인합니다.
- 해커톤 · 공모전뿐 아니라 일반 서비스 · 사내 프로젝트 · 기존 코드에 기능을 더하는 작업에도 씁니다. 처음에 정하는 **프로젝트 프로필**(혼자/팀, 화면 유무, 서버 유무, 대회 여부 등)에 따라 필요한 장만 고릅니다.

## 설치

Claude Code 안에서:

```
/plugin marketplace add kimyeongeuk/prd-spec
/plugin install prd-spec@prd-spec
```

터미널에서:

```bash
claude plugin marketplace add kimyeongeuk/prd-spec
claude plugin install prd-spec@prd-spec
```

설치한 뒤 Claude Code를 다시 시작하면 스킬이 잡힙니다.

| 하려는 일 | 명령 |
|---|---|
| 최신 버전으로 업데이트 | `claude plugin marketplace update prd-spec` → `claude plugin update prd-spec@prd-spec` |
| 삭제 | `claude plugin uninstall prd-spec@prd-spec` |

### 필요한 것

| 항목 | 용도 |
|---|---|
| Claude Code | 스킬 실행 |
| Node.js 20 이상 | 점검 스크립트 · PDF 읽기 스크립트 |
| npm · 인터넷 연결 | PDF 읽기 스크립트를 처음 실행할 때 `pdfjs-dist@4.10.38`을 임시 폴더에 설치 |
| (선택) [superpowers](https://github.com/obra/superpowers) 플러그인 | 마지막 "다음 문서 안내"에서 `superpowers:writing-plans`로 파트별 작업 계획을 이어 세울 때 |

## 사용법

### 부르는 법

PRD · 기능명세서 · 요구사항 문서를 쓰거나 고치자고 말하면 자동으로 불립니다.

```
docs/기획서.pdf로 개발할 거야. PRD랑 기능명세서 써 줘
```

직접 부를 때는 플러그인 이름을 붙입니다.

```
/prd-spec:prd-spec docs/기획서.pdf 기준으로 PRD와 기능명세서를 작성해 줘
```

입력 자료(기획서 PDF · 평가 기준 이미지 · 회의록 · 참고 문서)는 미리 프로젝트의 `docs/`에 넣어 두면 편합니다.

### 모드 A — 새로 작성

기준 문서가 없거나, 다른 형식으로 쓰인 문서를 새로 정리할 때입니다.

| 단계 | 하는 일 | 사용자가 할 일 |
|---|---|---|
| 1. 자료 읽기 | 기획서 본문과 그림까지 모두 읽고 결정 기록 파일을 만듭니다. 기획서가 "이미 했다"고 적은 작업(실험 · 분석 · 시제품)의 원자료가 없으면 그 작업을 한 사람에게 보낼 요청 문서를 만듭니다 | 원자료가 있는 곳, 작업한 사람을 알려 주기 |
| 2. 결정 인터뷰 | 프로젝트 프로필부터 시작해 갈래별로 **한 번에 하나씩** 묻습니다. 질문마다 맥락 · 선택지 · 추천과 이유 · "지금 정하지 않음"이 붙습니다 | 고르기("추천대로", 다른 답, 지금 정하지 않음) |
| 3. 장 목록 확정 | 프로필로 두 문서의 장을 고르고 번호를 매겨 보여 줍니다 | 장 목록 확인 |
| 4. 작성 | 문서 지도 → PRD → 기능명세서 → 점검 스크립트 복사 → (팀이면) 파트 안내 문서. 루트 `CLAUDE.md`에 공통 규칙을 덧붙이기 전에는 묻습니다 | 쓰다가 나온 "결정에 없던 것" 확인 |
| 5. 점검 | 점검 스크립트 오류가 0이 될 때까지 고칩니다 | — |
| 6. 완료 보고 | 완료 체크리스트를 표로 보고하고, 남은 미확정 · 회신 대기와 다음에 쓸 하위 문서를 안내합니다 | — |

git 커밋 · 저장소 생성은 요청할 때만 합니다.

### 모드 B — 갱신

이 스킬로 만든 문서가 있고 회신이 왔거나, 결정이 바뀌었거나, 구현이 문서와 달라졌을 때입니다.

```
AI 파트 회신이 docs/response/에 왔어. 반영해서 문서 갱신해 줘
```

바뀐 내용을 결정 기록에 적고 → 영향 범위(해당 U의 "정해지면 바뀌는 곳")를 찾아 → 두 문서를 함께 고치고 → 점검 → 체크리스트로 보고합니다. 해소된 U는 지우지 않고 `**확정 YYYY-MM-DD**: …`로 바꿉니다.

### 만들어지는 파일

```
docs/
├── PRD.md                  기준 문서 — 왜 · 누구 · 무엇 · 어디까지
├── 기능명세서.md            기준 문서 — 어떻게 동작하는가
├── README.md               문서 지도 (팀이면 변경 알림판 · 요청/회신 형식)
├── check-docs.mjs          두 문서 일치 점검 — 스킬 없이 저장소만으로 실행
├── 정리/결정-인터뷰.md       결정 기록 (기준 문서 아님)
├── request/{파트}/ · response/{파트}/    요청과 회신 (필요할 때)
{파트}/CLAUDE.md · README.md               파트 안내 (팀 · 에이전트 개발일 때)
```

### 문서에 쓰이는 ID

| ID | 뜻 | 정의하는 곳 |
|---|---|---|
| `F-영대문자-두자리` | 기능 | 기능명세서 기능 목록 |
| `R-영대문자-두자리` | 규칙 | 기능명세서 규칙 |
| `AC-영대문자-두자리` | 수용 기준 (검증하는 F를 함께 적음) | 기능명세서 수용 기준 |
| `S-두자리` · `A-두자리` | 화면 · API | 기능명세서 |
| `U-두자리` | 미확정 — 지금 아는 것 · 누가 정함 · 정해지면 바뀌는 곳 | PRD |
| `RK-두자리` · `E-두자리` | 위험 · 외부 근거 | PRD |
| `X-한자리` | 기획서 안에서 값이 서로 다른 곳 | PRD |

### 점검 스크립트

작성할 때 프로젝트 `docs/`로 복사되므로, 팀원은 스킬 없이도 돌릴 수 있습니다.

```bash
node docs/check-docs.mjs                                          # 두 기준 문서
node docs/check-docs.mjs --also CLAUDE.md app/CLAUDE.md            # 다른 파일의 절 · ID 참조까지
node docs/check-docs.mjs --self-test                              # 점검기 자체 시험
node docs/check-docs.mjs docs/PRD.md docs/SPEC.md                 # 파일 이름이 다를 때
```

- **오류**(종료 코드 1): 중복 정의 · 정의 없는 ID · 없는 절 · 수용 기준이 없는 기능 · PRD가 가리키지 않는 기능 · 미확정 표 빈 칸
- **경고**(사람이 판단): 아무도 가리키지 않는 미확정 · 설정값 반복 후보. 기획서 인용 · 용어 이름에 든 숫자 · 그 문서가 원본인 목표는 그대로 둡니다.
- 문서끼리 가리킬 때 쓰는 이름("PRD 7.3", "기능명세서 1.4")은 파일 이름에서 가져옵니다.

### PDF 읽기 스크립트

Read 도구로 PDF가 안 읽히거나 한글이 비어 나올 때 스킬이 알아서 씁니다. 직접 쓸 때는:

```bash
node <스킬 폴더>/scripts/read-pdf.mjs <PDF 경로> <출력 폴더>
```

쪽마다 텍스트를 `<출력 폴더>/text.txt`로, 내장 그림을 `p{쪽}_img{n}.png`로 꺼냅니다.

## 이 스킬이 하지 않는 것

- 공모전에 제출할 기획서 · 아이디어 소개서 · 발표 자료 작성
- API 계약서 · 작업 계획 · 화면 설계 같은 하위 문서 작성 — 각 파트가 기술 결정을 내린 뒤 쓸 문서라, 마지막에 누가 어디에 쓸지만 안내합니다
- 결정이 옳은지 판단 — 보장하는 것은 "지어낸 값이 없음 · 두 문서의 일치 · 빠진 갈래가 없음"까지입니다

```
.claude-plugin/
├── plugin.json
└── marketplace.json
skills/prd-spec/
├── SKILL.md                 흐름 · 원칙 · 모드 A/B
├── references/
│   ├── questions.md         인터뷰 갈래별 질문 · 추천 기준 · 답이 정하는 것
│   ├── templates.md         결정 기록 · 장 선택 · 두 문서 장 구성 · ID 규칙 · README · 요청 · 파트 안내 양식
│   └── checklist.md         완료 점검 (모드 A 16항목 · 모드 B 6항목)
└── scripts/
    ├── check-docs.mjs       두 문서 일치 점검
    └── read-pdf.mjs         한글 PDF 텍스트 · 그림 추출
```
